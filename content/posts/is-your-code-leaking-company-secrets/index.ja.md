## ユーザー列挙

こんなシナリオです。あるユーザーが私たちのシステムにメールアドレスでアカウントを登録しました。

その後、長期間システムを使用しなかったため、登録したことを忘れてしまい、同じメールアドレスで再度登録しようとしました。

一般的なウェブサイトのロジックでは、「このメールアドレスはすでに使用されています」とユーザーに知らせるはずです。

しかし、こんなシナリオを考えてみましょう：

> もしかしたらユーザーは、自分がアカウントを登録していることを他の人に知られたくないのではないか？

登録だけでなく、この問題は**「パスワードを忘れた」**というフローでもよく出てきます。

攻撃者は「パスワードを忘れた」ページにメールアドレスを入力し、システムが「このアカウントは見つかりません」と返答すれば、そのメールアドレスが登録されて**いない**ことが確認できてしまいます。

通常のウェブサイトではこの問題はないかもしれませんが、社会的に偏見を持たれやすいウェブサイトでは問題になる可能性があります。

余計なトラブルを避けるため具体例は挙げませんが、皆さんも考えてみてください XD

では、どうすれば解決できるでしょうか？よく使われる解決策を一つ紹介します：

ユーザーが入力したメールアドレスが存在するかどうかに関わらず、曖昧なメッセージを返します。例えば：**「このメールアドレスが私たちのシステムに存在する場合、パスワードリセットのメールが間もなく届きます。」** これにより、攻撃者はメールアドレスの有効性を判断できなくなります。

## ブラックリストとホワイトリスト

特定のサービスに特定のユーザーしかアクセスできないようにしたい場合、どちらを「優先的に」選ぶべきでしょうか？

- ブラックリスト：アクセスできない人を明示的に除外する

- ホワイトリスト：アクセスできる人を定義する

「両方使えばいいじゃないか」と思う方もいるかもしれません。確かに、この2つは排他的な関係ではないので、「優先的に」という言葉が重要です。

私個人の経験から言うと、ホワイトリストの方がほとんどの場合に適しています。

ホワイトリストが保証できることは：私が許可した人だけがアクセスできる、つまり入ってくる人は必ず私が知っている人だということです。

しかし、ブラックリストの場合、アクセスさせたくないすべての人をブロックできるとは保証できません。「認識している範囲内」でアクセスさせたくない人のみをブロックできるだけです。

「認識外」のアクセスさせたくない人は、まだサービスに入り込む可能性があります。

これはかなり大きなリスクです。どれほど経験豊富であっても、事前にすべての状況を考えることは難しく、一つでも抜けがあれば問題が生じる可能性があります。

## 試行回数が多すぎる場合

この話をすると、ある苦い経験を思い出します。

銀行のデジタル口座を初めて使い始めたとき、セキュリティを確保しようと、非常に複雑なパスワードを設定しました。

当時はまだパスワード管理ツールを使うという概念がなかったので、後にパスワードをすっかり忘れてしまいました。

しかも複雑なパスワードを設定したことも忘れていたため、ログイン時にいつも使うパスワードを試したところ、5回の試行でロックされてしまい、わざわざ銀行まで行かなければなりませんでした…🥲

多くのシステムに「何度エラーになったらアカウントをロックする」という仕組みがありますが、これはいわゆる辞書攻撃（Dictionary Attack）を防ぐためのものです。

しかし、この仕組みにはどんなリスクがあるでしょうか？

明らかに、誰かのアカウントを知っていて何度も試し続ければ、そのアカウントがロックされてしまいます。銀行デジタル口座の例では、相手は何度も銀行に行かなければならず、かなり不便です。

これはまだましな方で、「救済」措置がないサービスもあります。例えば fail2ban というパッケージは、SSH ログインの失敗が多すぎるとアカウントをロックします。

もし誰かがこの仕組みを悪用して、重要な運用担当者のアカウントを攻撃し続ければ、その担当者はサーバーにアクセスすらできなくなってしまいます……

誤解のないように言っておきますが、アカウントロック自体に反対しているわけではなく、その背後にあるリスクを指摘しているだけです。

## あなたの会社はどのくらいの規模？

フォーラムサイトを例にとると、一般的に記事の API はこのように設計されることが多いです：

```bash
GET forum.com/posts/1
```

このパターンは一見問題なさそうに見えますが、実はあるリスクが潜んでいます：会社の規模や成長速度が露わになってしまうのです。

例えば、`posts/1001` を見れば、このフォーラムの記事総数が 1001 件だとわかります。

また、`今月最後の記事の ID` から `今月最初の記事の ID` を引けば、今月追加された記事数がわかります。

毎月このデータを収集すれば、会社の成長速度がわかってしまうのではないでしょうか？

ここまで読んで、「わかった！じゃあ API に UUID や Slug を使えばいいじゃないか！」と思う方もいるかもしれません。

確かにその通りですが、重要なのは解決方法ではなく、**ビジネス上の意味を持つ、または列挙可能な ID を漏らさないこと**です。そうでないと、不必要な情報が露出してしまう可能性があります。

## 今、実際に何が起きているの？

多くの人がご存じかと思いますが、こんなステータスコードがあります：

```bash
429 Too Many Requests
```

問題はこうです。誰かが実際にレートリミットに引っかかったとき、フロントエンドにこのステータスコードを返すべきか、それとも `400` などのステータスコードを返すべきでしょうか？

一般的な会社は過度に厳しいレートリミットを設定しないので、引っかかる人のほとんどは自動化プログラムを動かしている人だと仮定できます。

そのような状況でボットが実行中に突然 `429` が返ってきたら、攻撃者は開始時刻からシステムのレートリミットルールを簡単に計算し、クローラー戦略を調整できてしまいます。

しかし `400` を返せば少し事情が変わります。攻撃者が `400` を見ても、必ずしもレートリミットの問題とは直結しないかもしれません。追加で実験を行わないと、レートリミットの閾値を正確に算出できないでしょう。

完全に閾値を推測されることを防げるわけではありませんが、少なくとも攻撃者の難易度を上げることができます。

もう一つ似た例として、フォームを設定した際に、ユーザーが何か入力ミスをした場合、どのフィールドが間違っているか、どのルールに違反しているかをユーザーに伝えるべきでしょうか？

「教えてあげればいいじゃないか、その方が便利だろう」と思う人もいるかもしれません。

確かに便利ですが、2つの状況を考える必要があります：

1. 上記のレートリミットと同様に、悪意のある人がシンプルな試行錯誤でどのデータがシステムに受け入れられるかを把握し、大量のスパムデータを送り続けてシステムをダウンさせようとする可能性があります。

2. 実際には多くのユーザーが入力習慣が悪く、データを適当に入力したり、余分な文字を打ったり誤字したりすることがよくあります。どこが間違っているか教えなければ、ユーザーはすべてのフィールドを注意深く確認するようになり、他の間違いを発見できる可能性が高まります。
