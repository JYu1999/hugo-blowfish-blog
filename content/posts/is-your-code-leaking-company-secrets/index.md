在當軟體工程師的這兩年，我遇過一些有趣的資安問題，想透過這篇文章和大家分享。

在實際開始前，先做個 disclaimer，我自己沒有很了解資安的定義是什麼，所以我不知道下面這些議題在嚴謹的定義下，算不算資安議題。不過反正我是都歸類在資安😆

## 使用者枚舉

情境是這樣子的，有個使用者在我們系統上，用了 Email 註冊了一個帳號。

後來他長時間沒有使用系統，所以他忘記他有註冊過了，因此他嘗試用他的 Email 進行註冊。

這個時候以一般網站的邏輯，應該會告訴使用者：「這個 Email 已經用過了。」

但我們可以想一個情境：

> 會不會使用者不希望被別人知道，他有註冊過？

除了註冊，這個問題也很常出現在 **「忘記密碼」** 的流程。

攻擊者可以在「忘記密碼」頁面輸入 Email，如果系統回應「查無此帳號」，就等於確認了哪些 Email **沒有**註冊。

正常的網站可能不會有這個問題，但一些比較容易被社會用異樣眼光看待的網站，可能就會有這個問題。

這邊怕惹麻煩就不舉例了，不過大家可以想想這個問題 XD

至於要怎麼解決呢？這邊提一個比較常見的解法：

無論使用者輸入的 Email 是否存在，都回傳一個模糊的訊息，例如：**「如果此 Email 存在於我們的系統中，您將很快會收到一封重設密碼的郵件。」** 這樣攻擊者就無法判斷 Email 的有效性。

## 黑名單與白名單

有時候某些服務，我們需要只能讓特定人存取，那這個時候，我們應該「優先」選擇哪一個呢？

- 黑名單：把不能存取的人明確排除

- 白名單：定義好可以存取的人

可能有些人的答案會是，兩個都用不就好了。確實這兩者並不是互斥的關係，所以「優先」這兩個字很重要。

以我個人的經驗來看，白名單會比較適合多數的情況。

白名單能確保的事情是：只有我開放的人才能存取，意味著進來的人，絕對不可能是我不知道的人。

但用黑名單，我不能確保所有我不想讓他存取的人，都不能存取。只能夠確保「認知範圍內」且不想讓他存取的人，不能使用服務。

而「認知範圍外」且不想讓他存取的人，還是有可能進入服務。

這個其實算一個蠻大的風險，因為就算經驗再怎麼豐富，也很難確保都能事先想到所有的狀況。只要有一個漏了，就有可能出問題。

## 有人試太多次

說到這件事情，就想到一個慘痛的經驗。

我剛開始使用銀行數位帳戶的時候，因為想確保安全，設定了一個超複雜的密碼。

那個時候也還沒有使用密碼管理工具的概念，所以後來密碼直接忘記。

而且我也忘記我設定了很複雜的密碼，後來登入的時候都用常用的密碼去試，結果嘗試了五次就被鎖，還要特別跑銀行一趟…🥲

相信在很多的系統「嘗試幾次錯誤就鎖帳號」的機制，這種機制在防範的是所謂的字典攻擊 (Dictionary Attack)。

但這個機制可能會有什麼風險呢？

很顯然的，如果我今天知道別人的帳號，然後去一直試，他帳號就會被鎖。以銀行數位帳戶的例子來說，就是別人要一直跑銀行，其實蠻不方便的。

這還算是比較好的情況，有些服務沒有可以「救援」的措施，例如在有一個套件叫 fail2ban，就是在 SSH 失敗太多次的時候，把帳號鎖住。

那如果有人利用這套機制，一直去攻擊重要維運人員的帳號，就會造成該人員連主機都進不去……

澄清一下，我並不是反對鎖帳號這件事情，只是提出背後的一個風險。

## 你的公司多大？

我們以一個論壇網站來說好了，一般來說文章的 API 可能會設計成：

```bash
GET forum.com/posts/1
```

這個模式乍看之下沒什麼問題，但其實它隱含著一個風險是：會透露公司的規模和發展速度。

比如說我看到 `posts/1001` ，我就知道現在這間論壇的文章總數有 1001 篇。

或是我可以用 `這個月最後一篇的 ID`，減去 `這個月第一篇的 ID` ，就知道這個月新增的文章數量有多少。

每個月都去統計這個數據，不就能知道公司的成長速度了嗎？

看到這邊一定會有人想：「我知道！那我 API 用 UUID 或是 Slug 不就解決了嗎？」

確實沒錯，但我認為重點不在解決方式是什麼，而是**不要洩漏具有業務意義或可被枚舉的 ID**，不然有可能會透露不必要的資訊。

## 現在到底是什麼狀態？

應該不少人知道，有一個 Status Code 是：

```bash
429 Too Many Requests
```

問題來了，當有人真的觸發 Rate Limit 的時候，我們應該給前端這個 Status Code，還是給前端 `400` 之類的 Status Code 呢？

一般公司不會設定過於嚴苛的 Rate Limit，所以我們可以假設會觸發的人，基本上都是寫自動化程式在刷的。

這種情況下，當機器人刷到一半，突然跳出一個 `429` ，那這位攻擊者基本上就能透過開始時間，很輕易的計算出系統的 Rate Limit 規則，進而調整爬蟲策略。

但跳 `400` 就不太一樣了，當攻擊者看到 `400` ，不見得會直接聯想到是 Rate Limit 的問題，他可能需要進行額外的一些實驗，才能真正算出 Rate Limit 的閾值。

雖然不能完全避免有人猜出 Rate Limit 的閾值，但至少也增加的攻擊者的困難。



另外一個類似的例子是，當我們設定一個表單的時候，假設使用者有填錯東西，要不要告訴使用者錯的是哪一格、違反了什麼規定？

看到這裡可能有些人會想說：「啊就跟他講啊，這樣不是比較方便？」

是很方便沒錯，但可能要思考兩個狀況：

1. 跟上面 Rate Limie 雷同，這樣有心人士就可以透過簡單的試錯，知道哪些資料系統會收，然後透過不斷發送垃圾資料，想辦法灌爆系統。

2. 其實很多使用者習慣很差，資料都隨便亂填，常常有多打字、打錯字的狀況。不跟使用者講錯在哪，他們反而會仔細去檢查所有的欄位，就有更高的機率可以發現其他的錯誤
