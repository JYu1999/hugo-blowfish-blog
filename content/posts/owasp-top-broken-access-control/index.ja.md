## Broken Access Control とは

Broken Access Control は OWASP の常連で、2021年には1位を獲得しており、その重要性が分かります。

簡単に言えば、Broken Access Control とは「ユーザーが本来行うべきでないことを行えてしまう」ことです。

アプリケーションはユーザーのアイデンティティと権限に基づいて、アクセスできる情報や実行できる機能を厳格に制限すべきです。

これらの制限措置に欠陥があり、簡単に回避できる場合、Broken Access Control と呼ばれます。

## 例

簡単な例を挙げて説明します。

今日、ある会社のウェブサイト管理者がいます。彼の仕事は会社の財務報告書、プレスリリースなどの関連情報を公開することです。

これらの情報は内部取引の疑いを避けるため、指定された時間に同時に公開されなければなりません。

時々業務が忙しく、指定時間に手動で公開できないため、「予約公開」機能を作りました。つまり情報は先に会社サイトに置かれますが、時間が来るまでは情報リストにリンクが表示されません。

各情報のURLには固定の書式があります。例えば四半期財務報告書のURLは：

```php
https://example-company/reports/2025-Q2.pdf
```

悪意ある人物はこの脆弱性を利用して、欲しい情報を取得しようとすることができます。

例えば、2025 Q3財務報告書の公開予定日の数日前、情報リストではまだ表示されていなくても、以下を試すことができます：

```php
https://example-company/reports/2025-Q3.pdf
```

関連情報を早期に入手できるかどうか試してみる。

もちろん、URLを改変して情報を取得することは、Broken Access Controlの一般的な方法の一つに過ぎません。

他の可能性としては、ユーザーが自分のアイデンティティをAdminなどに変更できるケースもあります。

## 防護戦略

上記の例を見て、「ではURLを予測不可能にすればいいのでは？」と言う人もいるかもしれません。

例えばURLをランダムな文字列にすることで、推測の難易度を上げることができます。

しかし経験のある人は、総当たり攻撃を試みたり、エンコードの方法を解析したりすることがあります。最終的にその情報が漏洩する可能性があるため、根本的な解決策にはなりません。

より完全な防護戦略には三つの環節が含まれます：

### 1. 認証(Authentication)

ユーザーがアプリケーションに戻るたびに、そのアイデンティティを正確に識別できること。これはすべての権限管理の出発点です。

### 2. 認可(Authorization)

ユーザーが認証を通過した後、システムはそのユーザーが許可されている操作と許可されていない操作を決定する必要があります。

### 3. 権限チェック

ユーザーが特定の操作を実行しようとした瞬間、システムはその認可状態をリアルタイムで評価し、その操作が許可されているかどうかを確認しなければなりません。

## 認可の一般的な実装方法

では、システムはどのような基準でユーザーが特定の操作を実行できるかを決定すればいいでしょうか？以下は一般的な方法です：

### 1. Role-based

これが最も一般的な認可方法で、各ユーザーに特定のロール（例：「管理者」と「一般ユーザー」）を割り当てることで権限を区別します。

### 2. 所有権に基づく認可

一部のリソースは特定のユーザーまたはグループに帰属し、その許可なしに他の人はアクセスできません。

### 3. ポリシーベースの認可

権限制御方式は通常「ポリシー(Policy)」の形式で定義され、どのエンティティやグループが特定の操作を実行できる（ホワイトリスト）か、できない（ブラックリスト）かを明確に定義します。

より複雑なシナリオでは、個別のファイルやデータに異なる権限を設定する必要があるかもしれません。この場合、より細かく具体的な権限管理方式を実装する必要があります。

## 設計と実装の四大指導原則

ソフトウェアエンジニアとして、実装前にどのようなことを考えるべきでしょうか？または実装時に注意すべきことは何でしょうか？

### 1. 最大リスクを評価・集中する

過剰も不足もいけないという概念は誰もが知っていますが、権限も同様です。早すぎる権限処理は、ビジネスロジックを複雑にし、メンテナンスコストを増やすだけです。

より良い方法は：製品や組織において絶対に漏洩させたり権限を取得されたりしてはならないものを特定し、それらを優先的に対処することです。

漏洩しても比較的深刻な影響がない情報は、後回しにしても構いません。

### 2. 事前設計と文書化

重要なものを定義したら、開発初期に設計と文書化を行うのが最善です。

権限を設計する際は、PMと十分に要件を確認することをお勧めします。共通認識のある規則がなければ、「正しい」実装とは何かを定義することは難しいです。

文書化は重要だと思います。時に権限制御はコードベースにしか存在せず、会社のPMや担当エンジニアでさえ現在の権限定義を把握していないことがあります。毎回コードベースを確認し直す必要があり、時間の無駄になります。

### 3. 権限決定の集中化を試みる

権限制御の判断ロジックをコードベースで集中管理することを目指すべきです。

これはすべてのリクエストが単一のコードパスを通らなければならないということではなく、関数デコレータ、パスチェック、データベースのストアドプロシージャ、または専用権限コンポーネントの呼び出しなどを用いた標準的な権限評価方法を確立すべきということです。

例として、Laravelにおける「非集中管理」は以下のようになります：

`PostController.php`の`update`内：

```php
<?php
public function update(Request $request, Post $post)
{
    // チェック1：ユーザーは記事の作者か？
    // チェック2：または、ユーザーは管理者か？
    if (Auth::id() !== $post->user_id && Auth::user()->role !== 'admin') {
        abort(403, 'Unauthorized action.');
    }

    // ...記事更新のロジック...
}
```

`PostController.php`の`destroy`内：

```php
<?php
public function destroy(Post $post)
{
    // ほぼ同じロジックを繰り返す
    if (Auth::id() !== $post->user_id && Auth::user()->role !== 'admin') {
        abort(403, 'Unauthorized action.');
    }

    // ...記事削除のロジック...
}
```

ビュー`show.blade.php`内で、編集ボタンを表示するか決定：

```php
@if (Auth::id() === $post->user_id || (Auth::check() && Auth::user()->role === 'admin'))
    <a href="/posts/{{ $post->id }}/edit">記事を編集</a>
@endif
```

これにはどんな問題があるでしょうか？

1. **重複**：同じ権限チェックロジックがControllerとViewなど複数の場所に散在している

2. **メンテナンス困難**：「編集者(editor)」も記事を修正できるようにしたい場合、すべての`if`判断を探し出して一つずつ修正する必要があり、見落としが非常に起こりやすい

3. **エラーが起きやすい**：一か所でもチェックを追加し忘れると、深刻なセキュリティ脆弱性が生じる



そのためLaravelでは、認可ロジックを集中管理するためのGatesとPoliciesを提供しています。具体的な実装方法の例：

1. まず集中した「規則の手引き」を作成する。ここでは`PostPolicy.php`を例として：

   ```php
   <?php


   class PostPolicy
   {
       // 「記事更新」のルールを定義
       public function update(User $user, Post $post): bool
       {
           // ルール1：ユーザーは記事の作者
           // ルール2：または、ユーザーは管理者
           return $user->id === $post->user_id || $user->role === 'admin';
       }

       // 「記事削除」のルールを定義
       public function delete(User $user, Post $post): bool
       {
           // ルールはupdateと同じでも異なってもよい
           return $user->id === $post->user_id || $user->role === 'admin';
       }
   }
   ```

2. 異なる場所でこの集中したルールを使用：

   ```php
   <?php
   public function update(Request $request, Post $post)
   {
       // LaravelはPostPolicyを自動的に見つけてupdateメソッドを呼び出す
       // ルールが通らない場合、403エラーを自動的にスロー
       $this->authorize('update', $post);

       // ...記事更新のロジック...
   }

   public function destroy(Post $post)
   {
       // 同様に、集中したdeleteルールを呼び出す
       $this->authorize('delete', $post);

       // ...記事削除のロジック...
   }
   ```

   ```html
   {{-- LaravelはPostPolicyを自動的に使って判断する --}}
   @can('update', $post)
       <a href="/posts/{{ $post->id }}/edit">記事を編集</a>
   @endcan
   ```

   ```php
   <?php
   // PostPolicyのupdateルールを通過したユーザーのみがこのrouteにアクセスできる
   Route::put('/posts/{post}', [PostController::class, 'update'])
        ->middleware('can:update,post');
   ```

### 4. 厳格で批判的なテスト

テストプロセスは権限制御方式の脆弱性を真剣に見つけ出そうとするものでなければなりません。攻撃者のように考えてテストすることで、実際の攻撃に備えることができます。予算と時間が許せば、外部チームによるペネトレーションテストの実施を検討すべきです。
