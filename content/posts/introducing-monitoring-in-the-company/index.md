一年多以前，我就想在公司導入監控系統。
 
當時去跟主管要權限，被一句「目前沒有需求」打了回票。說實話我也沒辦法反駁——系統看起來跑得好好的，沒有人覺得有問題。
 
但「看起來沒問題」跟「真的沒問題」，是兩回事。
 
## 兩起事件，同一個問題
 
最近連續發生了兩件事，讓我終於等到了機會。
 
**第一件：第三方服務故障了一個月，我們渾然不知。**
 
我們串接的某個第三方服務出了問題，導致特定情境下的申請流程全部失敗。發現之後，原因很快就釐清、修復也很迅速——但問題是，這個錯誤已經默默存在了至少一個月。是使用者來反映，我們才知道有這回事。
 
**第二件：伺服器換完三天後，假日炸了。**
 
公司剛換完一批伺服器，上線三天觀察下來一切正常。結果第四天是假日，使用者突然沒辦法上傳影片。等到有人來回報，我們才發現是一個設定值寫錯了。
 
這個錯誤持續了 12 小時。至少影響了兩位對公司很重要的使用者——之所以說「至少」，是因為只有兩個人主動回報。其中一位甚至直接在公開平台上抱怨，對公司的聲譽造成了實質打擊。
 
這兩件事的共同點很明顯：**出了問題，我們不知道；知道的時候，已經太晚了。**
 
背後其實有兩個結構性問題：一是因為歷史因素，沒有人對系統全貌有足夠的掌握，很多第三方服務的狀態處於黑箱狀態；二是缺乏監控機制，導致我們只能被動等使用者回報。而大多數使用者遇到問題的反應，其實不是回報，而是「算了」。
 
第二點才是最致命的。我之前在[這篇文章](/posts/unexpected-risks/)中聊過類似的想法：你以為風險是突然出現的，但往往它早就在那裡了，只是你一直沒看到。
 
這次的事件終於讓管理層正視了這個缺口。我也順勢自告奮勇，在工作空檔偷一點時間，開始推動監控的建置。

## 應用內：讓每一個 Exception 都被看見
 
我們的應用其實本來就有一套把錯誤發到 Slack 的機制，但實際運作下來有兩個問題。
 
### 「沒被 catch 的錯誤」等於不存在
 
原本的設計是：只有程式碼裡明確寫了 catch 的地方，才會發 Slack 通知。換句話說，那些沒有被 catch 住的錯誤，就這麼靜悄悄地直接到了使用者面前，工程師完全不知情。
 
如果 error handling 設計得夠完整，這個策略其實沒問題。但現實是，過去的程式碼有不少地方根本沒有寫好 catch。
 
所以我做的第一件事很粗暴：**只要有任何 Exception，全部發通知。**
 
這聽起來像是自找麻煩——Slack 不會被通知炸掉嗎？一開始確實會。但仔細想想：那些我們早就預料到、對系統也沒有實質影響的情況，本來就不應該被當成 Exception 拋出。它們應該被視為正常流程來處理。
 
所以這個策略的本質是：用短期的通知轟炸，換來長期的程式碼體質改善。隨著我們逐步把那些「假 Exception」從程式碼中清除，留下來的就會是真正需要關注的問題。
 
### 錯誤訊息只告訴你「壞了」，不告訴你「怎麼壞的」
 
另一個問題是：Slack 上的錯誤通知只會寫「某某情況錯誤」，不附帶具體的錯誤訊息。工程師每次都得自己連進伺服器翻 Log 才能搞清楚發生了什麼。
 
但很多錯誤其實一看訊息就知道原因了——網路抖動、金流商的系統異常，這些從 error message 就能直接判斷，根本不需要進伺服器。
 
所以第二個優化就是：**把錯誤的完整訊息一起送到 Slack**。讓工程師在 Slack 上就能快速分類：哪些需要深入調查、哪些只是外部因素造成的暫時性問題，省去不必要的 debug 時間。
 
## 應用外：用 New Relic 補上基礎設施的監控缺口
 
應用層內的警報做完了，但有些問題根本不在應用層——網路斷線、CPU 飆高、容器異常，這些情況下 request 可能根本進不來應用，或是應用本身已經跑不動了，應用層的錯誤通報自然不會有任何紀錄。
 
這部分我選了 New Relic 來處理，原因很簡單：公司其實一直都有在用，只是沒有好好利用而已。
 
因為時間有限，我先把範圍收在「已更換的新伺服器」上，只針對 CPU、GPU、Memory、Container、Network 這些基礎指標做監控。

舊伺服器因為短期內就會被替換，投入的效益不大，就先不處理。

至於 API 錯誤率、回應時間、排程執行狀況這些應用層指標，等之後有時間再補進去。
 
在設計 threshold 的時候，同事分享了一個我很認同的觀點：**寧可多報，不要晚報。**
 
以 CPU Usage 為例，與其一開始就設在 80%——等到觸發的時候使用者可能已經明顯感受到卡頓了——不如先設在 40%。如果太常被觸發，再往上調就好。先求「看得到」，再來調「看得準」。

## 裝好隔天就派上用場
 
New Relic 裝好之後的第一天，我就發現了一段詭異的空白：有整整半小時，完全沒有任何信號傳進來。
 
調查後才知道，那段時間機房的網路在進行維護。但重點是——**我們根本沒有收到任何維護通知。**
 
這讓我忍不住想：以前是真的沒問題，還是出了問題我們根本不知道？
 
更巧的是，隔天就有一位使用者回報：她在我們平台上傳訊息，一直傳不出去。工程師花了不少時間排查——看 Code、Debug、翻 Log，什麼異常都找不到。

照理說，訊息送不出去，應用層一定會有 Log 才對。
 
後來我去查了 DB 資料，發現這位使用者習慣在某個固定時段傳訊息。再一對時間——她反映問題的時間點，正好就是機房網路維護的時段。
 
Request 根本沒有進到應用，所以當然不會有任何 Log。而使用者因為沒有重新整理頁面，就一直停留在原處重試，也沒看到任何明確的錯誤提示。
 
如果沒有 New Relic 那段「信號消失」的紀錄，這個問題可能永遠查不出來。
 
## 寫在最後
 
我以前一直覺得，身為工程師，只要測試夠仔細、Code Review 夠嚴謹，就能確保自己做出來的東西沒問題。
 
但現實是：我們不可能預測所有狀況，犯錯是必然的。
 
所以真正該思考的，不只是「怎麼不犯錯」，而是「犯錯的時候，怎麼把傷害降到最低」——怎麼儘快發現、怎麼儘快止血。
 
這意味著在開發任何功能的時候，錯誤通報機制和監控指標不是事後補上的東西，而是應該跟功能本身一起被設計、一起被交付的。
 
推動這件事也帶給了我不小的成就感。畢竟這是從一年多前被打回票，到現在終於落地的事情。有時候不是時機不對，而是痛還不夠痛。等到真的痛了，機會自然就來了。
