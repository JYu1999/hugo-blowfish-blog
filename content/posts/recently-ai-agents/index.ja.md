最近、会社が遂にAIエージェントを本格的に導入してコードを書き始めました。

面白いことに、これを推進したのはエンジニアではなくPMでした。彼はプロダクトの方向性に対して明確な判断力を持っていますが、エンジニアリング開発の詳細については比較的疎いです。このことで私は気づきました。AIエージェントをエンジニアリング環境で本当に正常に機能させるには、**「AIを繋ぐ」だけでは不十分**であり、コンテキストとなる環境全体も一緒に構築しなければならないということです。

この記事では、私が今週行った調整とその背後にある考え方を共有したいと思います。

---

## 問題の発端：AIは私たちの開発環境を理解していない

最初にAIを動かしてみて、最初に直面した落とし穴は非常に直感的なものでした。

**AIは直接 `php artisan migrate` を実行しようとしますが、ローカルマシンにはそもそもPHPがインストールされていません。**

私たちのプロジェクトでは、Docker開発環境の管理にLaravel Sailを使用しており、すべてのコマンドは `./vendor/bin/sail` を経由して実行しなければなりません。このルールはエンジニアにとっては言うまでもないことですが、AIにとっては全くの未知です。

解決策は実は非常にシンプルです。`CLAUDE.md` にルールを追加し、**AIが開発作業を始める前に、開発環境の構築ドキュメントを読み**、このプロジェクトがLaravel Sailを使用している事実を理解するように要求するのです。

```md
<!-- CLAUDE.md -->
いかなる開発作業を始める前にも、必ず `docs/doc/fruktte/開發相關/開發環境建置.md` を読み、本プロジェクトがDocker開発環境の管理にLaravel Sailを使用していることを理解してください。

すべてのCLIコマンドは `./vendor/bin/sail` 経由で実行しなければならず、絶対にローカルで直接実行しないでください。
```

このことで、私は重要な概念を実感しました。`CLAUDE.md` は単なるルールリストではなく、AIの「オンボーディングドキュメント」なのです。新しいエンジニアが初日に知っておくべきことをすべて書き込む必要があります。

## 最初の大きな作業：煩雑なリリースフローの自動化

これ以前の私たちのリリースフローは次のようなものでした。

1. 完了したタスクをStageにマージする
2. 手動でStage → MasterのMRを作成する
3. 手動でコミットログを整理し、リリースノートを書く
4. 手動でリリース情報をSlackの#releaseチャンネルに投稿する

毎回リリースするだけで、コミットの整理、説明の作成、Slackへの投稿などにかなりの時間を費やしていました。最も面倒な部分は、MRのタイトルにフォーマットの規定があり、Slackのメッセージにも固定のフォーマットがあるため、毎回手動で照らし合わせる必要があり、ミスが起こりやすいことでした。

解決策：リリーススキル（Release Skill）を書く

私はこのフローを `fruktte-release-helper` というClaude Code Skillにパッケージ化することにしました。

全体のフロー設計は以下の通りです。

1. stageとmasterのコミットの差分を取得する
    ↓
2. 各コミットのカテゴリー（Feature / Fix / Change...）を自動分析する
    ↓
3. 分析結果を表示し、ユーザーの確認を待つ
    ↓
4. GitLabでドラフトPR（Stage → Master）を作成する
    ↓
5. Slackメッセージのドラフトを作成する
    ↓
6. ユーザーの確認を待ち、#releaseチャンネルに送信する

いくつかの設計上の決定事項について説明する価値があります。

- **常に先に表示し、その後に実行する。** 各重要なステップの前に、AIはまず分析結果を提示し、あなたの確認を待ってから続行します。コミットメッセージには曖昧さがある可能性が高く、AIの分類が100%正確とは限らないため、人間に最終確認をさせるのが安全なアプローチです。
- **Ready to Mergeではなく、ドラフトPRにする。** リリースPRは常にDraft状態で作成し、誰かが誤って直接マージボタンを押してしまうのを防ぎます。Reviewerの割り当てと最終的なマージは依然として人間が行います。
- **デプロイステップの検出はキーワードの推測ではなく、MRの説明を見る。** 今回のリリースでマイグレーションやcomposer installを実行する必要があるかどうかを知るための最も信頼できる方法は、コミットメッセージのキーワードをスキャンするのではなく、各FURチケットに対応するMRの説明を見ることです。AIは各MRの説明を自発的にチェックしに行きます。

現在、リリースフローは次のようになっています。

AIに「リリースしたい」と伝える → AIがすべての整理とPR作成を自動で行う → 確認する → Slackメッセージの送信完了

エンジニアは2つの確認ポイントで頷くだけで、残りはすべて自動化されます。

## 2つ目の改善：MRの作成も自動化する

同様の問題は日常のMRでも発生していました。私たちのMRタイトルにはフォーマット規則があります。

`FUR-{番号} {Jiraチケット名}`

以前は、MRを作成するために以下の手順が必要でした。
1. Jiraに行ってチケットの完全なタイトルを調べる
2. それをコピーする
3. GitLabに貼り付け、正しいフォーマットに組み合わせる
4. MRにJiraチケットのリンクを貼り付ける

些細なことに聞こえますが、何十回も繰り返すと非常に面倒になります。

私はこれを `fruktte-create-mr` スキルとしてまとめました。AIは次のように動きます。
1. 現在のgitブランチ名からFUR番号を抽出する
2. Jira MCPを使用してチケットのタイトルを自動的に検索する
3. 正しいフォーマットに組み合わせて、MRを作成する
4. MRにJiraチケットのリンクを添付する

同時に、ブランチのフォーマットに基づいてターゲットブランチも判断します。
- feature/FUR-{番号} → stageにマージ
- task/FUR-{子番号}/feature/FUR-{親番号} → 対応するfeature/ブランチにマージ

現在、MRを作成するには「MRを作成して」と一言言うだけで、残りはAIがすべて引き受けてくれます。

## 3つ目の改善：MCPを個人設定からプロジェクトレベルに移行する

導入の初期段階では、MCP（Model Context Protocol：AIを外部ツールに接続するためのプロトコル）の設定は各開発者のローカルマシン（ユーザースコープ）に置かれていました。

これはいくつかの問題を引き起こしました。

1. ツールを統一的に管理できない。例えば、私たちのGitLab MCPにはマージツールがあります。AIに直接マージを手伝わせたくないのですが、ユーザースコープではそれを統一的に無効化することが難しいです。
2. サブエージェント（SubAgent）の権限を分離できない。今後、異なる役割のSubAgentが登場した場合、理論的には各役割は必要なツールのみを使用できるべきです。例えば、「バックエンドエンジニア」SubAgentはJiraの読み取り権限を持つべきですが、Figmaの編集権限は持つべきではありません。
3. 開発者の個人設定と混ざってしまう。会社の設定と個人の設定が干渉しやすく、メンテナンスが困難になります。

解決策は、MCP設定をプロジェクトスコープに移行すること、つまり設定をコードベースに付随させることです。

```text
.mcp.json             ← ローカルの実際の設定（gitignoreし、コミットしない）
.mcp.json.example     ← 設定テンプレート（コミットし、全員の参照用とする）
.claude/settings.json ← Claude Codeのプロジェクトスコープ設定
```

exampleファイルのパターンを使用することで、各開発者はどの設定が必要かを知ることができますが、実際の認証情報（credentials）はバージョン管理に入りません。このアプローチはエンジニアによく知られている `.env.example` の概念と全く同じです。

## 全体的な振り返り：このプロセスから学んだこと

これらすべてを終えて、AIエージェントをエンジニアリングフローに導入する際の課題は、AI自体が十分に強力かどうかではなく、必要な環境やルールを適切に構築しているかどうかにあると感じました。

いくつかの教訓。

- **毎回説明し直すのではなく、繰り返される決定をスキル（Skill）としてパッケージ化する。** MRタイトルのフォーマットやリリースフローの手順など、これらのルールを毎回自然言語の記述に頼るのは非常に脆弱です。それらをスキルとしてまとめることで、AIは毎回同じフローを実行し、結果は安定して予測可能になります。
- **CLAUDE.mdはAIのオンボーディングドキュメントである。** AIを本当にプロジェクト内で機能させるには、使用するツール、コマンドの実行方法、存在する仕様など、新しいエンジニアが知っておくべきことをすべて書き込む必要があります。
- **AIが重要な操作を実行する前に、必ず確認ポイントを設ける。** AIの分析結果は必ずしも100%正確ではありません。重要なノードで人間が確認することは、品質を保つための最後の防衛線です。完全自動化は魅力的ですが、まだ十分に信頼できない部分に手動確認を残すのは正しい選択です。
- **MCPはユーザースコープではなく、プロジェクトスコープに置くべきである。** ツールの管理、権限の分離、設定の混乱の回避など、これらはすべてエンジニアリングの基本的な衛生的習慣であり、MCP管理も例外ではありません。

---

現在、これらのツールはチーム内でしばらくの間稼働しています。リリースフローの効率は明らかに向上し、「MRタイトルのフォーマットを忘れる」や「Slack通知を漏らす」といった人為的ミスも大幅に減少しました。

AIは銀の弾丸ではありませんが、必要なコンテキストを構築するために時間をかける意思があるなら、反復的で精神力を消耗する作業の多くを省くのに確実に役立ちます。
