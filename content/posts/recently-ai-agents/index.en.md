Recently, our company finally started officially adopting AI Agents to write code.

Interestingly, the person pushing for this was a PM, not an engineer. Although he has clear judgment on the product direction, he is relatively unfamiliar with the details of engineering development. This made me realize: if we want AI Agents to truly work normally in an engineering environment, **just "plugging in the AI" is not enough**; you have to set up the entire context environment along with it.

This article aims to share the adjustments I made this week and the thinking behind them.

---

## The Starting Point of the Problem: AI Doesn't Understand Our Development Environment

After getting the AI to run initially, the first pitfall we encountered was very straightforward:

**The AI would directly execute `php artisan migrate`, but PHP wasn't even installed on the local machine.**

Our project uses Laravel Sail to manage the Docker development environment, and all commands must be executed via `./vendor/bin/sail`. This rule is extremely familiar to engineers, but the AI knows absolutely nothing about it.

The solution is actually quite simple: add a rule in `CLAUDE.md`, **requiring the AI to read the development environment setup documentation before starting any development work**, to understand the fact that this project uses Laravel Sail.

```md
<!-- CLAUDE.md -->
Before starting any development work, please read `docs/doc/fruktte/開發相關/開發環境建置.md` to understand that this project uses Laravel Sail to manage the Docker development environment.

All CLI commands must be executed via `./vendor/bin/sail`. Never execute them directly on the local machine.
```

This made me realize an important concept: `CLAUDE.md` is not just a list of rules; it's the AI's "onboarding document." You have to write down everything a new engineer needs to know on their first day.

## The First Major Undertaking: Automating the Tedious Release Process

Before this, our release process looked like this:

1. Merge completed tasks to Stage
2. Manually open a Stage → Master MR
3. Manually organize the commit log and write release notes
4. Manually post the release information to the Slack #release channel

Every time we released, just organizing commits, writing descriptions, and posting to Slack took quite a bit of time. The most annoying part was that MR titles have specific format requirements, and Slack messages also have a fixed format. Having to manually check these every time makes it easy to make mistakes.

Solution: Write a Release Skill

I decided to wrap this process into a Claude Code Skill called `fruktte-release-helper`.

The entire process is designed as follows:

1. Get the commit differences between stage and master
    ↓
2. Automatically analyze the category of each commit (Feature / Fix / Change...)
    ↓
3. Display the analysis results and wait for user confirmation
    ↓
4. Create a draft PR in GitLab (Stage → Master)
    ↓
5. Generate a draft Slack message
    ↓
6. Wait for user confirmation, then send it to the #release channel

A few design decisions are worth explaining:

- **Always display first, then execute.** Before every critical step, the AI will first display the analysis results for you to see, and only continue after you confirm. Because commit messages can often be ambiguous, the AI's classification might not be 100% accurate, so having a human make the final confirmation is a safe approach.
- **Draft PR, not Ready to Merge.** Release PRs are always created in a Draft state to prevent someone from accidentally hitting merge directly. Reviewer assignment and the final merge are still done by humans.
- **Detect deployment steps by looking at the MR description, not by guessing with keywords.** To know whether this release needs to run a migration or composer install, the most reliable way is to look at the MR description corresponding to each FUR ticket, rather than scanning the commit message for keywords. The AI will proactively check the description of each MR.

Now the release process has become:

Tell the AI "I want to release" → AI automatically completes all organization and PR creation → Confirm → Slack message creation complete

Engineers only need to nod at two confirmation points, and the rest is fully automated.

## The Second Improvement: Automating MR Creation Too

A similar problem also occurred with daily MRs. Our MR titles have formatting rules:

`FUR-{Number} {Jira Ticket Name}`

Previously, to open an MR, you had to:
1. Go to Jira and look up the full title of the Ticket
2. Copy it
3. Paste it into GitLab and combine it into the correct format
4. Paste the link to the Jira Ticket on the MR

It sounds small, but after repeating it dozens of times, it gets very annoying.

I wrapped this into the `fruktte-create-mr` skill. The AI will:
1. Grab the FUR number from the current git branch name
2. Use the Jira MCP to automatically query the Ticket title
3. Combine them into the correct format and create the MR
4. Attach the link to the Jira Ticket on the MR

At the same time, it will also determine the target branch based on the branch format:
- feature/FUR-{Number} → merge to stage
- task/FUR-{Sub-number}/feature/FUR-{Parent-number} → merge to the corresponding feature/ branch

Now, to open an MR, you just need to say "help me open an MR," and the AI handles the rest.

## The Third Improvement: Moving MCP from Personal Settings to the Project Level

In the early stages of adoption, MCP (Model Context Protocol, which allows AI to connect to external tools) settings were placed on each developer's local machine (user scope).

This brought about several problems:

1. Tools couldn't be centrally controlled. For example, our GitLab MCP has a merge tool—we don't want the AI to directly help with merging, but under user scope, it's hard to uniformly disable it.
2. The permissions of SubAgents couldn't be isolated. If there are SubAgents with different roles later, theoretically each role should only be able to use the tools it needs. For example, a "Backend Engineer" SubAgent should have Jira access, but shouldn't have Figma editing access.
3. Mixed with developers' personal settings. Company settings and personal settings easily interfere with each other and are hard to maintain.

The solution was to move MCP settings to the project scope, meaning the settings follow the codebase:

```text
.mcp.json             ← Actual local settings (gitignored, not committed)
.mcp.json.example     ← Settings template (committed, for everyone's reference)
.claude/settings.json ← Claude Code project scope settings
```

By using the example file pattern, every developer knows what settings are needed, but the actual credentials don't enter version control. This approach is identical to the concept of `.env.example`, which engineers should be very familiar with.

## Overall Review: What I Learned from This Process

After doing all this, I feel that the challenge of introducing AI Agents into an engineering workflow doesn't lie in whether the AI itself is strong enough, but in whether you have properly set up the environment and rules.

A few takeaways:

- **Wrap repetitive decisions into Skills, instead of re-explaining them every time.** MR title formats, release process steps—relying on natural language descriptions for these rules every time is very fragile. By wrapping them into Skills, the AI will follow the exact same process every time, making the results stable and predictable.
- **CLAUDE.md is the AI's onboarding document.** To make the AI truly able to work in your project, you must write down everything a new engineer needs to know: what tools to use, how to execute commands, and what specifications exist.
- **Before the AI executes critical operations, there must be confirmation points.** AI analysis results aren't necessarily 100% accurate. Having humans confirm at critical nodes is the last line of defense for maintaining quality. Full automation is tempting, but keeping manual confirmation in places where trust is not yet sufficient is the right thing to do.
- **Put MCP in the project scope, not the user scope.** Tool control, permission isolation, avoiding configuration confusion—these are all basic engineering hygiene habits, and MCP management is no exception.

---

Currently, these tools have been running in the team for a while. The efficiency of the release process has noticeably improved, and human errors like "forgetting the MR title format" or "missing Slack notifications" have been significantly reduced.

AI is not a silver bullet, but if you are willing to spend the time building the context it needs, it can indeed help you save a lot of repetitive and mentally draining work.
