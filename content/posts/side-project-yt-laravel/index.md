最近我花了一些時間做了一個 Side Project，是一個 Youtube 影片下載工具。

它最後沒有走到我一開始幻想的「做成產品、開會員、接廣告」那條路，但它確實解決了我當下的問題，也讓我對「做 Side Project 的核心哲學」有了更清楚的理解。

如果你也曾經想做 Side Project 卻遲遲沒開始、或是做著做著就放棄，或許這篇文章可以帶給你一些啟發。

---

## 為什麼我以前總覺得 Side Project 很有壓力？

以前別人問我「你有在做 Side Project 嗎？」我常常會回答：

> 沒有欸，因為我沒有什麼問題需要用 Side Project 來解決。

但後來我慢慢發現，這句話其實只說對一半。

更真實的原因是——我覺得做 Side Project 的成本太高了。

* 要設計功能
* 要寫程式
* 要部署
* 要維護
* 可能還要做行銷

如果我現在遇到的問題沒有大到需要付出這些成本，那我自然會覺得「Side Project 很重」，甚至開始逃避。

---

## Mentor 給我的一個超重要觀念：先設定「失敗目標」與退場機制

上週我和一位 mentor 聊天，他分享了一個我非常認同的做法：

### ✅ 做 Side Project，可以一開始就把「失敗目標」寫清楚

例如：

* 一週內它沒有產生每月 1,000 元台幣的收益
* 每個禮拜要花五小時以上維護

只要這個 Side Project 達成「失敗目標」，就可以直接放棄。

這聽起來有點反直覺，因為我們習慣把目標設定成「成功條件」。

但對 Side Project 來說，反而應該先把**停止條件**寫清楚。

這就像投資一樣：可以期待獲利，但控制風險需要的是「停損點」

### ✅ 放棄不是問題，「不知道為什麼放棄」才是問題

Mentor 也提到他以前做 Side Project 最痛苦的一點：只要中途放棄，他就會產生很強的罪惡感。

而這個罪惡感會讓他下次更不想開始新的 Side Project，因為大腦會直接把 Side Project 連結成「恐怖的事情」。

所以他建議我：

> 你可以放棄，但最好放棄得有理由。

做法就是：當你想放棄時，把原因記錄下來。

久了你會更了解自己「什麼情況下容易放棄」，下次在設定 Scope、訂退場機制時就更有依據，也更能預判風險。

---

## 我現在覺得 Side Project 的第二重要原則：快速上線、快速驗證

Side Project 當然要解決問題，這永遠是第一優先。

但我覺得第二重要的是：

> **Side Project 必須追求快速迭代。**

因為 Side Project 和商業工作最大的不同是：

* 它沒有穩定收益
* 沒有合約
* 沒有客戶在催
* 你完全靠意志力在推進

如果你花了大量時間卻一直沒有上線，那對自己來說會是很大的士氣打擊。

因此我更傾向這個流程：

1. 先做 Prototype（甚至還不到 MVP）
2. 先上線
3. 先測試真實環境
4. 再決定是否值得繼續往下做

為什麼我會傾向這個流程，或許可以看看我下面的案例。

---

## 這次的 Side Project：一個 YouTube 影片下載服務

這次我做的 Side Project 很簡單。

我一直都有下載 YouTube 影片的需求，之前是透過「yt-dlp」這個 CLI 工具。但我常常會忘記指令，因為我每次要下載的格式可能不同，而且有的時候還需要下載字幕。

某天，我女朋友突然跟我說她想下載 YouTube 影片，但她不知道怎麼做。

我想：

> 既然我大概知道怎麼弄，那我就來做一個簡單的下載工具吧。

### 我做了什麼？

我大概花了兩三天把整個功能做完，包含：

* 貼上 YouTube 影片網址
* 下載影片（mp4，最高畫質）
* 下載字幕
* Docker/DB/Cache/Queue/快取等基礎架構

在本地測試一切正常，我可以順利下載影片。

但在這時，我面臨關於 MVP Scope 的掙扎，例如：

* 要不要加會員系統？
* 要不要接廣告？
* 要不要把限流做完整？

限流服務的部分我猶豫最久：因為是線上服務，可能會被濫用，而且硬體性能有限，所以應該要有流量相關限制，例如單一 IP 同時只能下載 1 部，或全系統同時最多下載 10 部。

雖然 MVP 應該越簡單越好，但它終究是一個 **Product**。所以我認為攸關於系統穩定性的東西就是要在 MVP 階段就做好的。

但我算了一下工期：

* 核心下載功能已經做了 3 天
* 限流做完可能要再多 1～2 天
* 而且限流做出來後，我自己使用也會被限制，還要幫自己開後門，又會多花幾天

這樣整個驗證速度會被拖慢。

在 Side Project 裡，**核心功能能不能 work，比「附加功能做得多完整」重要太多**。

如果我先花時間把限流做完，結果上線後發現 YouTube 根本擋 Data Center，那我做的限流幾乎毫無價值。

所以我最後選擇遵循「快速上線」的原則——

> 先上線再說。

---

## 上線後我才發現的真相：本地可行 ≠ Production 可行

服務上線後，我直接撞到最大的問題：

> **無論如何都下載不下來。**

我查了一下才知道：

* YouTube 有反下載的機制
* 它會偵測 IP 是否是 Data Center
* 如果你是在雲端機器（例如 AWS）跑下載，它可能直接阻擋

這個問題非常關鍵，因為它完全不是「我再加會員系統就能解決」的事情。

你如果要繼續做，可能會走向這些方案：

* Proxy / 代理池
* Cookie 登入
* 其他繞過策略

但我當下的直覺是：

> 這也太麻煩了吧。

我只是想做一個「下載 YouTube」的工具，結果我要在 Production 上搞一堆反爬對抗、資安成本、維運負擔。

這就開始偏離了我做 Side Project 的核心目的。

---

## 但我沒有覺得可惜，因為我快速上線才快速得到答案

這就是我覺得最爽的一件事：

* 如果我沒有上線
* 我在本地測得再爽

我永遠不會知道 Production 根本跑不起來。

也就是說：

> **快速上線，讓我快速獲得「不值得投入」的證據。**

這比花三週做完整 MVP，最後才發現不行，省太多時間。

---

## Docker 帶來的體悟：快速部署就是快速驗證的基礎建設

以前我部署專案通常是手動 SSH 下指令、手動裝環境。

這次我刻意用 Docker 做一鍵部署，因為我想把「快速驗證」做到極致。

而我也真的感受到 Docker 的美好：

* 需要重建環境？刪掉重開就好
* 機器太小裝不起來？換一台更大的再跑一次就好
* 上線測錯？改完直接重新部署

這種「可重複、可快速、可復原」的部署方式，對 Side Project 來說超級重要。

甚至我覺得在這個時代：

> Infrastructure as Code（Docker、Script、Ansible）可能比功能本身更重要。

原因是 Side Project 的環境與需求變動速度太快了，你需要的是可以快速重來、快速嘗試的能力。

而且在 AI 時代，這類工具也更適合跟 AI 搭配：

* AI 產生 Dockerfile / Script，你直接執行
* 不需要一行一行人工貼指令

這會讓你的迭代速度直接提升。

---

## 我最後選擇放棄：因為它會變成一場永恆的貓抓老鼠

在評估之後，我決定停止這個 Side Project。

原因很單純：

* 商業價值不高
* 對抗 YouTube 反下載機制會是長期負擔
* IP 有可能被封
* 政策隨時可能改

這會變成一場永恆的「貓抓老鼠」遊戲。

而我做 Side Project 的本意是：

> 解決我的問題，而不是變成我新的焦慮來源。

如果只是放個廣告賺點外快、服務不太需要管，那可以。

但如果我要長期擔心它會不會壞掉、會不會被封，那就不符合我的期待。

---

## 但問題仍然被解決了：用 Cloudflare Tunnel 把服務跑在自己的電腦

放棄 Production 上線，不代表這個專案完全沒用。

後來我找到一個折衷方案：

* 我把服務跑在自己的電腦上（Docker 起起來）
* 用 Cloudflare Tunnel 對外開一個入口
* 女朋友要用的時候跟我說
* 我就把 Tunnel 開起來

她就可以用手機或電腦直接連到我本機的服務，照樣下載影片。

這樣的好處是：

* 不需要在 AWS（Data Center）環境被 YouTube 擋
* 不需要 Proxy
* 不需要維運一個永遠在線上的服務
* 我自己也能用

核心目的依然達成。

---


## 總結：我從這次 Side Project 得到的 3 個收穫

### 1) Side Project 不一定要成功，但要有退場機制

你可以允許自己放棄，但最好放棄得有理由、有紀錄。

### 2) 快速上線、快速驗證，比做一個完整 MVP 更有價值

尤其當你要驗證的是「Production 會不會踩雷」。

### 3) Docker / IaC 是 Side Project 的加速器

它幫你把「部署成本」壓到極低，讓你更敢嘗試、更快迭代。

---

如果你也正在猶豫要不要做 Side Project，我想送你一句我現在最相信的話：

> **快速上線，快速失敗，才是最有效率的成功路線。**
