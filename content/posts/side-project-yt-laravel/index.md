最近我花了一些時間做了一個 Side Project，是一個 Youtube 影片下載工具。

它最後沒有走到我一開始幻想的「做成產品、開會員、接廣告」那條路，但它確實解決了我當下的問題，也讓我對「做 Side Project 的核心哲學」有了更清楚的理解。

如果你也曾經想做 Side Project 卻遲遲沒開始、或是做著做著就放棄，或許這篇文章可以帶給你一些啟發。

---

## 本來覺得 Side Project 很重，直到我看見新的可能

以前別人問我「你有在做 Side Project 嗎？」我常常會回答：

> 沒有欸，因為我沒有什麼問題需要用 Side Project 來解決。

但後來我慢慢發現，這句話其實只說對一半。

更真實的原因是——我覺得做 Side Project 的成本太高了。

* 要設計功能
* 要寫程式
* 要部署
* 要維護
* 可能還要做行銷

如果我現在遇到的問題沒有大到需要付出這些成本，那我自然會覺得「Side Project 很重」，甚至開始逃避。

直到這次，我決定試試看完全不同的做法。

---

## 策略篇：先寫好「遺書」，再開始寫 Code

上週我和一位 Mentor 聊天，他也提到了我想要開始 Side Project，但卻擔心成本太高的問題。

他分享了一個我非常認同的做法：

### ✅ 做 Side Project，可以一開始就把「失敗目標」寫清楚

例如：

* 一週內它沒有產生每月 1,000 元台幣的收益
* 每個禮拜要花五小時以上維護

只要這個 Side Project 達成「失敗目標」，就可以直接放棄。

這聽起來有點反直覺，因為我們習慣把目標設定成「成功條件」。但對 Side Project 來說，反而應該先把**停止條件**寫清楚。

這就像投資一樣：可以期待獲利，但控制風險需要的是「停損點」。

「停損點」就是一個最壞的狀況，當已經知道最壞的情況是什麼了，那「開始行動」就不會感覺這麼恐怖了。

所以，我這次為這個 YouTube 下載器設了三個停損點：

1.  我只願意付一台 VPS 的錢（約 $5/month）
2.  我不希望花超過 20 小時開發 & 上線
3.  如果不符合預期（例如維護成本過高），立即停止，絕不戀戰

---

## 執行篇：3 天衝刺，做一個「最簡陋」的下載器

這次的題目很簡單：我女朋友想下載 YouTube 影片，但她不知道怎麼用 CLI 工具。我想說既然我會寫程式，不如做個網頁版給她用。

我大概花了兩三天把整個功能做完，包含：

* 貼上 YouTube 影片網址
* 下載影片（mp4，最高畫質）
* 下載字幕
* 基礎架構（Docker/DB/Queue）

### 來自「完美主義」的誘惑

在開發過程中，我其實面臨過關於 MVP Scope 的掙扎。

當時 AI 建議我：「因為是線上服務，可能會被濫用，應該做限流（Rate Limit），例如單一 IP 同時只能下載 1 部，或是全系統同時最多下載 10 部。」

這聽起來非常合理。我也一度猶豫：

* 要不要加會員系統？
* 要不要接廣告？
* 要不要把限流做完整？

但我算了一下工期：核心功能已經做了 3 天，限流做完可能要再多 1～2 天，而且這還會限制我自己使用，我還得幫自己開後門。

這樣整個驗證速度會被拖慢。

最後我心裡的一個聲音說服了我：「**你都還沒確定這東西在 Production 能不能跑，做那麼多保護機制幹嘛？**」

況且，萬一上線後根本沒人要用，或是核心功能在正式環境有問題，那我現在花時間刻的限流功能就全是白工。

與其糾結這 1% 的風險，不如趕快上線看看能不能跑。

所以我最後選擇遵循「快速上線」的原則——**先上線再說。**

---

## 撞牆篇：被現實狠狠打臉

服務上線後，我直接撞到最大的問題：

> **無論如何都下載不下來。**

我查了一下才知道，YouTube 有反下載的機制，它會偵測 IP 是否是 Data Center。如果你是在雲端機器（例如 AWS EC2）跑下載，它可能直接阻擋。

這個問題非常關鍵，因為它完全不在我的預想中。

如果要繼續做，可能會走向這些方案：

* Proxy / 代理池
* Cookie 登入
* 其他繞過策略

但我當下的直覺是：**這也太麻煩了吧。**

我只是想做一個「下載 YouTube 影片」的工具，結果我要在 Production 上搞一堆反爬蟲，此外如果要 Proxy 的話，還會增加成本。

### 觸發停損點

這時候，我回去看我一開始設下的「失敗目標」：

1.  **成本不可控**：如果要買 Proxy，成本絕對超過 $5/month。
2.  **維護成本過高**：這會變成一場永恆的貓抓老鼠遊戲，YouTube 改演算法，我就要跟著改。

這直接就觸發了我的「停損點」了。

如果我當時花了三週把會員系統、限流機制全部做完才發現這件事，我大概會崩潰。但因為我只花了三天，所以我可以很冷靜地接受這個事實。

---

## 結案篇：有尊嚴的放棄，與折衷方案

在評估之後，我決定停止這個 Side Project 的 Production 上線計畫。

但我沒有覺得可惜，這就是我覺得最爽的一件事：**快速上線，讓我快速獲得「不值得投入」的證據。** 這比花三週做完整 MVP 最後才發現不行，省太多時間。

### 轉個彎：Cloudflare Tunnel

雖然放棄上線，但不代表這個專案完全沒用。

後來我找到一個折衷方案：

* 我把服務跑在自己的電腦上（Docker 起起來）
* 用 Cloudflare Tunnel 對外開一個入口
* 女朋友要用的時候跟我說，我就把 Tunnel 開起來

她就可以用手機或電腦直接連到我本機的服務，照樣下載影片。

這樣的好處是：

* 本機 IP 通常不會被 YouTube 擋
* 不需要 Proxy
* 不需要維運一個永遠在線上的服務
* 我自己也能用

核心目的依然達成，但我成功避開了無底洞般的維護成本。

---

## 總結：技術與心態的雙重成長

這次 Side Project 雖然「失敗」了（沒能變成一個公開服務），但我卻覺得收穫滿滿。

### 1) Side Project 的「止損學」

Mentor 說的沒錯：「不知道為什麼放棄」才是問題。但我這次放棄得非常清楚、非常有理由。甚至可以說，**「有理由的放棄」本身就是一種成功。**

### 2) 快速上線的價值

在 Side Project 裡，**核心功能能不能 work，比「附加功能做得多完整」重要太多**。尤其當你要驗證的是「Production 環境會不會踩雷」這種未知風險時，速度就是你的保命符。

### 3) 意外的技術收穫：Docker / IaC

雖然功能沒做大，但我這次刻意用 Docker 做一鍵部署，卻意外變成了我最大的收穫。

以前我部署專案通常是手動 SSH 下指令，這次我體驗到了「可重複、可快速、可復原」的美好。

* 需要重建環境？刪掉重開就好。
* 上線測錯？改完直接重新部署。

甚至在 AI 時代，AI 幫我寫 Dockerfile，我直接執行，這讓我的迭代速度快了不只一倍。這也讓我體悟到：**Infrastructure as Code 可能比功能本身更重要，因為它是讓你敢於快速嘗試的底氣。**

---

如果你也正在猶豫要不要做 Side Project，我想送你一句我現在最相信的話：

> **快速上線，快速失敗，才是最有效率的成功路線。**
