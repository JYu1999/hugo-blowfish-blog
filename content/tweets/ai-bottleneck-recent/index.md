[軟體工程佔了 AI Agent 近 50% 的 Agentic API 呼叫 — 從數據看 Agent 自主性的現實與未來](https://blog.aihao.tw/2026/02/23/agent-autonomy-domains/)

看到這篇文章，跟自己的想法蠻相似的，紀錄一下。

主要是這一段：

> 研究用了一個很棒的概念:「deployment overhang」— 模型的能力已經到了，但實際部署的自主程度遠遠落後。
>
> METR 的評估顯示 Claude Opus 4.5 能處理人類要花近 5 小時才能完成的任務，但 Claude Code 的 99.9th percentile 自主工作時間才 45 分鐘，中位數更只有 45 秒。
>
> 這個落差對做產品的人來說就是機會: 不是模型不行，是產品層面的信任機制、監控工具、權限控制還沒做好。誰能在垂直領域把這些做好，誰就能釋放 agent 的潛力。

我覺得現在 AI 在開發上是完全沒問題了，應該有不少工程師都是用 AI 在開發和 Trace Code、Debug。

但目前我觀察大多數 Production 產品，最終還是會有人工 Review。這也代表一件事情：無論 AI 產生程式碼的速度有多快，最終還是會被 Review 的速度卡住。

我覺得底層的原因是源自於 LLM 的本質：它是一個預測機率的模型。

所以哪怕只有 0.01% 的機會線上環境有可能出問題，都是不可以接受的。

那這個問題怎麼辦？難道永遠被 Review 的速度卡住？

當然沒有人知道未來到底會如何，不過我想大膽猜測一下要進一步解放 AI 的生產力，可能需要的基礎建設：

1. 文件化：有的時候 AI 會做出錯誤的判斷，源自於 context 不足。這時候如果文件夠完善，AI 就能更準確地判斷，減少錯誤發生的機率。此外我們也會希望 AI 不要犯同樣的錯誤
2. SRE：既然 AI 沒辦法 100% 正確，那就要有完善的監控和回滾機制。如果機制夠完善，我們就能接受 AI 犯錯，因為我們知道「就算有錯我們也能快速收到通知，並快速修正」。
